# กฎการตรวจคุณภาพ (Quality & Verification)

> เป้าหมาย: งานที่ AI ตัวไหนก็ตามทำ ต้อง**พิสูจน์ได้ว่าถูก** ไม่ใช่แค่ "บอกว่าเสร็จ"
> ใช้คู่กับ Definition of Done ใน [workflow.md §4](workflow.md)

---

## 1. คำสั่งตรวจ (ต้องรันก่อนบอกว่าเสร็จทุกครั้ง)
| คำสั่ง | ตรวจอะไร | เวลาโดยประมาณ |
|---|---|---|
| `npm run typecheck` | TypeScript ทั้ง `src/` และ `tests/` | ~5 วิ |
| `npm run test` | unit test (Vitest — `tests/unit/**` และ `src/**/*.test.ts` คู่ไฟล์ใน feature) — แผนที่ทุกพื้นที่ event เซฟ ภูมิศาสตร์ คำต้องห้าม กฎโค้ด | ~5 วิ |
| `npm run build` | production build | ~2 วิ |
| `npm run e2e` | เปิดเกมจริง (Playwright, Chromium) บน 4 ขนาดจอ (มือถือแนวตั้ง/แนวนอน, แท็บเล็ต, เดสก์ท็อป) — console error, audit ทั้งหมด, เซฟ/โหลด, ทุกแผนที่ render + ถ่ายภาพหน้าจอ | ~1 นาที |
| **`npm run check`** | **ทั้งหมดข้างบนตามลำดับ** | ~1–2 นาที |
- `npm run check` ต้องผ่าน 100% ก่อนส่งงาน — **ห้ามลบ/ข้าม/ลดเงื่อนไข test เพื่อให้ผ่าน** ถ้า test ผิดเอง ให้แก้ test พร้อมอธิบายเหตุผลในรายงาน
- `npm run test:watch` ใช้ระหว่างทำงานได้
- e2e ต้อง build ก่อน (ใช้ `vite preview` ที่พอร์ต 4173) — `npm run check` ทำให้อัตโนมัติ
- ครั้งแรกบนเครื่องใหม่: `npx playwright install chromium`

## 3. เมื่อเพิ่มงานใหม่ ต้องเพิ่ม test อะไร
| งาน | ต้องทำ |
|---|---|
| prop ชนิดใหม่ในแผนที่ | เพิ่มใน `PROP_ZONES` (`src/world/map-audit.ts`) — ถ้าลืม test จะแจ้ง "unknown prop type" |
| จังหวัด/อำเภอ/ย่านใหม่ | ไม่ต้องเขียนเพิ่ม — `maps.test.ts` + `geo-config.test.ts` วนทุกพื้นที่อัตโนมัติ; ทำตามสูตร [maps.md §2](maps.md) และดูภาพ |
| ช่องค่าตั้งแผนที่ใหม่ใน `geo.json` | เพิ่ม type ใน `src/world/geo.ts` + ค่าที่ยอมรับใน `geo-config.test.ts` |
| อาคารหลักใหม่ที่ทุกแผนที่ต้องมี | เพิ่มใน `REQUIRED_BUILDINGS` (`maps.test.ts`) |
| event ใหม่ | ไม่ต้องเขียนเพิ่มถ้าอยู่ใน pool เดิม; pool ใหม่ → เพิ่มใน `buildAuditContext()` (`events.test.ts`) และใน `auditContext()` ของเกม |
| op / requires key ใหม่ | เพิ่ม test ใน `events.test.ts` ส่วน ops engine |
| field ใหม่ใน state | เพิ่ม expect ใน test "เซฟรุ่นเก่า" ว่าได้ค่า default |
| เปลี่ยนโครงเซฟ | **เพิ่มไฟล์เซฟตัวอย่างใหม่** ใน `tests/saves/` (ห้ามแก้ไฟล์เก่า) + test โหลด |
| ฉาก/โหมดใหม่ | เพิ่ม test ใน `smoke.spec.ts` + ถ่ายภาพหน้าจอ |
| feature ใหม่ | `<name>.service.test.ts` คู่ไฟล์ (ผลปกติ · กรณีขอบ · state ไม่หลุดกรอบ) + e2e ถ้ามีหน้าจอใหม่ ([architecture.md §7](architecture.md)) |
| สูตรเงิน/เวลาใหม่หรือแก้สูตร | เขียน/แก้ใน `src/sim/` (ไม่ใช่ใน `game.ts`) + unit test ใน `economy.test.ts` + อัปเดต GDD |
| คำต้องห้ามใหม่ | เพิ่มใน `ROYAL_TERMS` / `BRAND_TERMS` (`content.test.ts`) |

## 4. ตรวจด้วยตา (เครื่องตรวจแทนไม่ได้)
- หลัง `npm run e2e` ภาพหน้าจออยู่ที่ `test-results/screens/<mobile-portrait|mobile-landscape|desktop>/`
- **ต้องเปิดดูภาพของฉากที่งานแตะทุกครั้ง** และเทียบกับกฎ [art.md](art.md) / [ux-ui.md](ux-ui.md): อะไรผิดที่ ล้นจอ ตัวอักษรชน ไฟเปิดกลางวัน ภาพจมความมืด
- ถ้าเป็นงานภาพ ให้แนบ/อ้างชื่อภาพที่ตรวจในรายงาน
- **[อนาคต]** ภาพ baseline + เทียบอัตโนมัติ (visual regression) หลังย้ายเป็น 32px เสร็จ — ตอนนี้ภาพเปลี่ยนบ่อยเกินไป

## 5. ตรวจทาน (Review) — ห้ามตรวจงานตัวเองอย่างเดียว
งานที่เข้าข่ายข้อใดข้อหนึ่ง ต้องให้ **AI ตัวที่สอง (หรือ session แยก) ตรวจ** ก่อนเจ้าของรับงาน:
- แก้ไฟล์ > 300 บรรทัด หรือแตะ > 5 ไฟล์
- แตะระบบเงิน เซฟ เวลา หรือการเกิด event
- เพิ่มเนื้อหาที่อยู่ใน [content-safety.md](content-safety.md) §2 (เขตเทา)
- เปลี่ยนกฎใน `AGENTS.md` / `docs/rules/`

ผู้ตรวจต้อง:
1. อ่านกฎหมวดที่เกี่ยวข้องก่อน
2. อ่าน diff ทั้งหมด (ไม่ใช่แค่สรุปของคนทำ)
3. รัน `npm run check` เอง
4. รายงานเป็นรายการ: ปัญหา · ไฟล์:บรรทัด · ร้ายแรงแค่ไหน · วิธีแก้ที่เสนอ
5. ไม่แก้เองเงียบ ๆ — แจ้งคนทำหรือเจ้าของ

## 6. บั๊กที่รู้แล้ว
- จดใน [`docs/BUGS.md`](../BUGS.md) ทุกครั้งที่เจอบั๊กแต่ยังไม่แก้ (รวมบั๊กนอกขอบเขตงาน)
- รูปแบบ: `id` · อาการ · วิธีทำให้เกิด · ไฟล์ที่น่าจะเกี่ยว · ความรุนแรง (สูง/กลาง/ต่ำ) · สถานะ
- แก้บั๊กแล้ว → ย้ายไปหัวข้อ "แก้แล้ว" พร้อมบอก test ที่กันไม่ให้กลับมา
- **บั๊กที่แก้แล้วต้องมี test กันกลับมา** ถ้าเขียน test ได้

## 7. เมื่อทำพัง (Incident)
1. หยุดเพิ่มงานใหม่ทันที
2. บอกเจ้าของตรง ๆ: พังอะไร ตั้งแต่เมื่อไร กระทบผู้เล่น/เซฟหรือไม่
3. ถ้าย้อนได้ง่าย → ย้อนเฉพาะส่วนที่พัง (ไม่ใช้คำสั่ง git ที่ทำลายงานอื่น เช่น `reset --hard`, `checkout .` โดยไม่ถาม)
4. เขียน test ที่จับปัญหานี้ได้ แล้วจึงแก้
5. จดใน `docs/BUGS.md` หัวข้อ "แก้แล้ว" พร้อมสาเหตุ
- เพราะเจ้าของจัดการ git เอง: ก่อนงานใหญ่ ให้แนะนำเจ้าของ commit/สำรองก่อนเริ่ม และจดรายการไฟล์ที่จะแตะไว้ในรายงาน

## 8. ข้อห้าม
- ห้ามบอกว่า "ผ่าน" ถ้าไม่ได้รันจริงในรอบนั้น (ผลจากรอบก่อนไม่นับ)
- ห้ามปิด/ลบ test, เพิ่ม `.skip`, ลดเงื่อนไข หรือเพิ่มข้อยกเว้นใน audit เพื่อให้ผ่าน โดยไม่ได้รับอนุญาต
- ห้ามแก้ไฟล์เซฟตัวอย่างเก่าใน `tests/saves/`
- ห้ามปล่อย `console.error` ในโค้ด (DoD ต้องไม่มี console error) — ใช้ `console.warn` สำหรับสิ่งที่กู้คืนได้
- ถ้ารัน `npm run check` ไม่ได้ (เช่น ไม่มีเบราว์เซอร์) ต้องบอกในรายงานว่าข้ามขั้นไหน
